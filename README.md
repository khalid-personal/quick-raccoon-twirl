## Local development

```sh
pnpm install
cp .env.example .env.local
pnpm dev
```

The package manager is pinned to pnpm 10.24.0. Publish `package.json` and `pnpm-lock.yaml` together whenever dependencies change. Vercel uses a frozen lockfile; verify with `pnpm install --frozen-lockfile` and `pnpm build` before deploying. Do not disable frozen-lockfile checks to hide a manifest mismatch.

Replace the Supabase URL and anon key in `.env.local` with the project values before using live authentication. The anon key is intended for browser use; never put a service-role key or payment secret in a `VITE_*` variable or commit `.env.local`.

Keep `VITE_USE_LOCAL_MOCK=true` while local records are not imported. This prevents an empty Supabase database from replacing the local data cache. Set it to `false` only after completing the Supabase activation checks below.

## Supabase activation

The browser uses `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY`. Server-side functions use `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`. Keep the service-role key server-only.

Before enabling Supabase data mode:

- Apply and verify row-level security policies for every application table, including role and agency ownership restrictions. The checked-in migration currently covers Realtime presence only.
- Import the existing local records first. The linked project’s checked application tables were empty during the last audit; enabling sync before import can make the portal appear blank.
- Verify sign-in, hydration, writes, and role isolation against the deployed project.

The Supabase CLI schema pull was blocked by the database role’s permissions. Do not treat the current RLS state as verified.

## Vercel deployment

Vercel discovers TypeScript functions under `api/` automatically. `vercel.json` supplies the SPA fallback; the payment handlers are in `api/chechepay/`.

Set these variables in Vercel’s project settings, not in client-exposed variables:

- `SUPABASE_URL`
- `SUPABASE_SERVICE_ROLE_KEY`
- `CHECHE_SECRET_KEY`
- `CHECHE_FINANCE_BASE_URL`
- `CHECHE_APP_URL`
- `CHECHE_STAGE_FEES_JSON`

Use the ChechePay test key in Preview while validating the hosted checkout and return verification. Test a successful, pending, failed, and repeated verification before switching to a live key. The local Vite middleware serves the ChechePay handlers during development; it does not emulate Vercel’s deployment environment.

## Integrations

Candidate stage fees use hosted ChechePay checkout and server-side final verification. Foreign-agency settlement is intentionally demo-only until a provider and settlement contract are selected.

Candidate receipts preserve available ChechePay confirmation fields and can be viewed/printed after checkout and from Payment History. The viewer generates a portal receipt, not a ChechePay-issued PDF. Candidate collections use provider status: pending, payment failed and payment timed out remain unpaid. Only foreign-to-local transfers appear in the dashboard discrepancy review and bank statement tools. Live ChechePay failure/timeout delivery still requires the final integration; the portal does not invent provider outcomes.

Payment History status tiles filter the ledger across role portals. The compact USD overview sums only settled foreign-agency transfers using the reference rates in `src/lib/currency.ts`; it is an estimate, not live FX or bank-confirmed USD. Unsupported currencies are reported as excluded, and original currency totals remain available. Superadmin investigation views distinguish payment initiators from recorders/verifiers, show linked candidate activity and related transfers, and support evidence requests and escalation in the local case log. Historical actors are never inferred when attribution is missing. Case notes are local to the browser; no external inquiry notification is sent.

Candidate intake is now **ministry-managed through ELMIS**. Manual creation is removed from the dashboard and rejected by the candidate API. The official ELMIS API contract and server credentials are not available yet: no live candidate fetch or synchronization is claimed. Existing candidates remain available in their agency scope. The internal ministry-feed reconciliation helper matches official candidate IDs, Labor IDs and normalized passports, merges repeated records without changing existing profile/tracking IDs or operational evidence, rejects ambiguous identity collisions and unknown local agencies, and uses the ministry's local-agency assignment. It is not connected to an external API yet. Labor IDs and ELMIS registration details are displayed separately; missing official details stay labeled as awaiting ministry data.

Passport image/PDF uploads up to 15 MB still read names, DOB, gender, passport number, nationality, issuing country, expiry and document type when readable. PDFs use embedded MRZ text when available; image-only PDFs still render and OCR up to five pages. MRZ does not supply birthplace, home city, marital status, contact details or skills. Reviewed scans now attach only to a unique existing passport match within the account's allowed candidate scope. Missing/ambiguous matches explicitly stop the upload; no new candidate is created. Original candidate identity and agency assignment remain unchanged. Scanned identity differences and repeated Labor IDs create separate integrity findings rather than being hidden by a healthy aggregate score. Staff cannot manually reassign the managing local agency or edit ELMIS details.

The demo sandbox preserves existing evidence. The six scenario switches generate foreign-transfer shortages, overpayments and missing bank entries, while candidate stage-fee amounts stay exact and unsuccessful attempts show failed/timed-out provider statuses. Unsuccessful payments never get invented deposits. Existing uploaded statements and operator case edits are protected. These are illustrations, not real bank proof, and are never seeded into live statement storage.

Evidence requests have optional submission-window start dates and required deadlines, including the whole deadline day in Addis Ababa time. Notes do not cancel open requests; a resolution does. Current, fully verified payment records also stop obsolete reminders without deleting historical request snapshots; removing proof makes the request active again. The waiting room filters pending, due-soon and overdue requests. Local managers, assigned staff and superadmins receive scoped in-portal reminders, refreshed on focus, case changes and every minute while the portal is running. Reminder acknowledgments are browser-local and never sent to Supabase as bank evidence. No email/SMS delivery or closed-browser scheduling is implemented.

**Settings → Ministry submission calendar** lets a signed-in superadmin set an audited start/deadline for all new candidate submissions. Candidate profiles and deployment snapshots show this window. New payment proof requests and fresh resolution escalations inherit its deadline; existing issued requests retain their own dates and history. Until a ministry window is saved, new submissions default to the current Addis Ababa date through seven days later, explicitly labeled as a default. Scheduled windows stay scheduled and expired windows remain overdue until explicitly replaced; invalid dates are rejected rather than rolled forward. Ordinary settings saves preserve the calendar. This is a portal calendar, not an official external ministry submission.

The Payment History heading includes a live **Ministry tracker** countdown (days/hours/minutes/seconds). It counts to midnight after the entire Ethiopian deadline day, counts to opening for scheduled windows, and explicitly shows overdue for expired windows. Calendar changes refresh it without resetting payment filters or open reviews; an unsaved calendar is labeled as a default, not a ministry-issued deadline.

Escalation requires a reason and follow-up deadline. Foreign agencies have **three chances per ministry cycle**: the first two distinct verified bank underpayments open audited warnings/follow-ups; the third pauses new operations.
